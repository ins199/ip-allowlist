# Bug 修复方法论

> **核心原则：不要直接改代码。先追踪完整数据流，找出所有受影响的地方，再动手。**

## 一、常见 bug 模式（对照检查）

修 bug 前看一眼，判断属于哪种：

| # | 模式 | 一言蔽之 |
|---|------|---------|
| 1 | 状态同步遗漏 | 改了 A 忘了同步 B（store/iptables/前端三处一致性）|
| 2 | 持久化遗漏 | 内存改了没落盘，重启丢 |
| 3 | 幂等缺失 | 重复执行/重复请求产生重复数据或规则错乱 |
| 4 | 防锁死绕过 | 删当前 IP / 删到空 / 严格模式空白名单裸 DROP |
| 5 | 前端与后端不一致 | API 返回 vs 页面渲染字段/状态不符 |
| 6 | 鉴权遗漏 | 新接口没挂 authGroup 或跳过中间件 |
| 7 | XSS/注入 | 前端未 `esc()` 转义、命令拼接未校验 |
| 8 | 解析/格式 | IP/CIDR 解析、IPv6 冒号截断、时间格式 |

## 二、修 bug 前必须做的三件事

### 1. 追踪实际执行路径

```
入口 handler → 实际执行的函数 → 改了什么（store 落盘 / iptables 应用 / 前端数据）
```

### 2. 追踪完整数据流

用户操作 → api handler → store（JSON 落盘）→ iptables（规则生效）→ 前端展示，**逐环节检查一致性**。

### 3. 复现/验证（禁止猜）

- 本地 `IPAW_DRY_RUN=1` 起服务，curl 复现
- 对比 `allowlist.json` 与 iptables 状态是否一致
- 涉及防火墙：dry-run 打印规则确认顺序（先 ACCEPT 后 DROP）

## 三、提交前自检

- [ ] 完整追踪了数据流（api/store/iptables/前端）
- [ ] 持久化与内存一致（重启不丢）
- [ ] 防锁死用例走查（删当前 IP / 删到空 / 严格模式空白名单）
- [ ] 返回字段只增不删，类型不变
- [ ] 错误分支有日志，不吞错误

## 四、修复后出报告

```
根因类型：[状态同步 / 持久化 / 幂等 / 防锁死绕过 / 前后端不一致 / 鉴权 / XSS / 解析]
影响范围：涉及哪些文件、哪条链路
修改内容：改了什么，为什么这样改
验证方法：哪些用例测试
潜在风险：还有哪些地方没把握
```

## 五、记录

修复后在 `plans/plan.md` 变更日志追加一行（日期 + fix 内容）。
